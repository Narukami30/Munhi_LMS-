# NMHS SERMS

Node.js and Express application for the NMHS SERMS pages, backed by MongoDB. The HTML layouts and styles remain in place; Express serves the pages and the shared client script sends their workflows to the API.

## Run locally

1. Install Node.js 20 or later and run MongoDB locally, or create a MongoDB Atlas database. Without `MONGODB_URI`, development mode connects to `mongodb://127.0.0.1:27017/naujan_mhs_serms`; MongoDB must be running there.
2. Copy `.env.example` to `.env` and set the identifier, email address, and password for each role you want to seed. Unconfigured roles are skipped. If using MongoDB Atlas or another MongoDB server, also set `MONGODB_URI`. Set a unique `SESSION_SECRET` before deployment. Seed passwords must be at least 12 characters and contain uppercase and lowercase letters, a number, and a symbol.
3. Install dependencies and create the initial accounts:

   ```powershell
   npm.cmd install
   npm.cmd run seed
   npm.cmd start
   ```

4. Open `http://localhost:3000`. Choose the appropriate role on the public portal and sign in with the matching values from `.env`.

The seeded accounts are created or updated by role and identifier. Keep `.env` private. Do not use development credentials or the development session secret in production.

## Deploy to Render

1. Push the project to a private GitHub repository. Confirm `.env` is not committed; `.gitignore` excludes it and other `.env.*` files while allowing `.env.example`.
2. Create a MongoDB Atlas database in a region close to the Render service. Create a database user with access only to this application's database, enable TLS, and copy its connection string. Configure the Atlas network access list for Render's outbound IP addresses if available; otherwise, Atlas may require `0.0.0.0/0`, which permits connection attempts from any IP and must be paired with a strong, restricted database user.
3. In Render, choose **New > Blueprint**, connect the repository, and deploy `render.yaml`. Enter the Atlas connection string for `MONGODB_URI` when prompted. The Blueprint configures the Node service, production mode, one trusted proxy hop for Render's HTTPS proxy, a generated session secret, and `/api/health` health checks. The free plan may spin down when idle and has no persistent local disk; application data is stored in MongoDB.
4. Create the initial accounts once against the Atlas database. From a trusted machine, use a private local `.env` with the Atlas `MONGODB_URI` and the required `SEED_*_IDENTIFIER`, optional `SEED_*_EMAIL`, and `SEED_*_PASSWORD` values, then run `npm.cmd run seed`. The `.env` is git-ignored; never put database credentials or seed passwords in source control. Alternatively, use a Render shell if available on your selected plan. Remove temporary seed credentials from the service environment after seeding.
5. Configure `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, and `MAIL_FROM` in Render if production account recovery by email is required. Recovery intentionally returns unavailable in production until SMTP and sender details are configured.
6. Wait for Render's health check to pass, then open the service URL. Verify staff sign-in, protected dashboard access, enrollment submission/tracking, and password-recovery email delivery (if configured) before sharing it with users.

Do not commit production `.env` files. Render's `SESSION_SECRET` is generated by the Blueprint; keep it stable as the application's secret key. Login sessions use an additional process-specific signing key, so stopping or restarting the server invalidates existing logins and requires users to sign in again. Use a separate production MongoDB database, restrict database permissions and network access, configure backups, and follow school-approved privacy and retention policies before adding real learner records.

## Connected workflows

- Role-specific sign-in and protected student, teacher, registrar, and principal dashboards.
- Student self-registration using a 12-digit LRN, verified-format email address, and strong password; student accounts remain inactive until a registrar approves them. Registrars can approve or reject requests with a review note. Approved students can use account recovery through their registered email.
- Student dashboard with the signed-in learner's linked enrollment status, grade/program, section when assigned, submission date, tracking code, saved attendance, and approved grade-submission assessment scores. Students without an existing enrollment record can submit a separate application directly from the dashboard while enrollment is open; the signed-in account's LRN is read-only and enforced by the API. The form is hidden when an application already exists, preventing duplicate submissions.
- Teacher, registrar, and principal profile settings for updating the account name and email or changing a password after confirming the current password.
- Online enrollment submission, review status, and public tracking by a high-entropy tracking code (not by LRN); the principal can manage the public portal's school year, enrollment availability, homepage copy, announcements, contact details, school-reported statistics, and logo.
- Registrar live enrollment and document-request summaries, database-backed enrollment review and document processing, and CSV exports for enrollment and document-request records.
- Principal-managed teacher class rosters containing officially enrolled learners; teacher views and record submissions are restricted to those assignments.
- Teacher attendance, grade drafts/submissions by teacher-entered subject or learning area across three terms, anecdotal records, and attendance CSV exports.
- Principal live enrollment, faculty, staff-account, and grade-submission summaries; teacher/registrar account provisioning and activation/deactivation; faculty records; grade review; and an audit log.
- Principal CSV downloads for enrollment applications, saved attendance, grade submissions, and audit events. These exports reflect stored SERMS data and are not certified DepEd forms.
- Password recovery with expiring, single-use verification codes and helpdesk tickets.

The account recovery portal returns an OTP in API responses only when `NODE_ENV` is not `production`. Configure `SMTP_HOST` and `MAIL_FROM` to deliver production recovery emails; recovery codes are sent only to the active account's registered email address. SMS delivery is not configured and is disabled in the portal. Recovery helpdesk tickets are saved in SERMS and can be reviewed and updated in the registrar dashboard. Password resets require at least 8 characters with upper- and lowercase letters, a number, and a symbol.

Principals can deactivate teacher and registrar accounts without deleting their records; protected requests from an already signed-in deactivated account are rejected. Principal broadcasts are stored in SERMS but are not pushed to other portals or sent as SMS. DepEd LIS/PSA integrations are not configured: no approved external endpoints or credentials were provided, and no records are synchronized. SF4, SF5, SF10, and BEIS exports remain unavailable because the required movement, promotion, transcript-history, and facilities data are not stored. Production use also requires HTTPS, database backups, and school-approved privacy/retention policies.

## API

The API is same-origin under `/api`. `GET /api/health` reports application/database readiness, `GET /api/public/content` returns the public portal's saved settings, `POST /api/student-registrations` submits a student account for approval, `GET /api/public/summary` returns aggregate enrollment counts, `GET /api/student/dashboard` returns the signed-in student's own enrollment, attendance, and approved grade details, and `GET /api/enrollments/track/:reference` looks up enrollment or document status by tracking code. Sessions use HTTP-only cookies stored in MongoDB. The Express server exposes only the named HTML pages and `/assets`; it does not publish `.env` or server source files as static content.

Principal-only endpoints include `GET /api/principal/overview`, `GET /api/principal/accounts`, `PATCH /api/principal/accounts/:id/status`, and `PUT /api/principal/public-content` for updating public portal settings. Logo uploads are limited to PNG, JPEG, or WebP images of at most 750 KB. Class rosters are managed through `GET /api/principal/rosters`, `GET /api/principal/rosters/learners`, and `PUT /api/principal/rosters`; only active teacher accounts and officially enrolled learners can be assigned. Teacher rosters are available only to the signed-in teacher at `GET /api/teacher/rosters`, and grade, attendance, and anecdotal writes are checked against those assignments. CSV exports are available at `/api/principal/reports/enrollments.csv`, `/attendance.csv`, `/grades.csv`, and `/audit.csv`; each export is generated from the corresponding records stored in MongoDB.

Registrar-only endpoints include `GET /api/registrar/overview`, `GET /api/registrar/student-registrations`, `PATCH /api/registrar/student-registrations/:id`, `GET /api/helpdesk`, `PATCH /api/helpdesk/:id/status`, `PATCH /api/documents/:tracking/status`, and CSV exports at `/api/registrar/reports/enrollments.csv` and `/api/registrar/reports/documents.csv`. Registrar dashboards load student registration, enrollment, document-request, and recovery-helpdesk records from MongoDB. Only the registrar can approve or reject self-registered student accounts. Enrollment status can be reviewed in SERMS; the dashboard does not perform PSA or DepEd LIS verification. Transfers, certified DepEd forms, and historical SF10 transcripts are unavailable because their underlying records are not stored in SERMS.

Teachers can download their saved attendance at `/api/teacher/reports/attendance.csv`. Class schedules and official SF9/report-card generation are not available because those records are not stored in SERMS.
